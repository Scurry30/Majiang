# 规则集架构：如何在同一套 App 里切换日麻 / 温岭

## 结论先说

「切换规则」能做，但**不是换一份配置**。现有 `majiang-core` 是日麻专用引擎，
牌组、手牌张数、向听公式、和牌型、计分方式全部写死；温岭麻将在这五项上都不同。
可行且成本可控的做法是：

> 一套外壳（页面/牌图/CSS/交互） + 两套引擎（core / wenling） + 两套视图

选规则 = 选引擎 + 选视图，而不是给同一套引擎喂不同参数。

## 为什么不能只改配置

| 日麻假设 | 代码位置 | 温岭的差异 |
|:--|:--|:--|
| 136 张，34 种 × 4 | `core/lib/shan.js:23-30` | 144 张：+8 花牌，共 42 种 |
| 牌名 `m/p/s 1-9`、`z 1-7` | `core/lib/shoupai.js:9` | 需要花牌（`f1-f8`）与财神标记 |
| 手牌 13 张 | `core/lib/xiangting.js:13` | 16 张 |
| 和牌型 = 4 面子 + 1 将 | `core/lib/hule.js:40-63` | 待定（见待确认 ①） |
| 向听 = 张数差公式 | `core/lib/xiangting.js` | 财神是万能牌，需带通配的搜索 |
| 符 + 番 → 点数表 | `core/lib/hule.js:598` 起 | 胡头 + 台数，且闲家两两差额 |
| 立直/宝牌/门风 | `majiang-ui/lib/board.js` | 财神/花牌/台数/胡头，无立直宝牌 |
| 流局 = 摸到王牌 | `core/lib/game.js:972` | 剩 8 墩（16 张）即流局 |

## 目标架构

```
Majiang/
├── src/js/rulesets/index.js     规则集注册表（id / 名称 / 引擎 / 视图 / 人数）
├── src/js/rulesets/riichi.js    日麻适配器：包 core + majiang-ui
├── src/js/rulesets/wenling.js   温岭适配器：包 core-wenling + ui-wenling
└── src/html/page/               对局页按规则集拆（或一个页面按 id 装配）

matiang-core/      (现有) 日麻引擎          ─┐
majiang-wenling/   (新)   温岭引擎          ─┤ 同一消息协议：
                                           │   kaiju / qipai / zimo / dapai /
majiang-ui/        (现有) 日麻视图 + 公共件 ─┤   fulou / gang / hule / pingju
majiang-wenling-ui/(新)   温岭视图          ─┘   + 各自的 view.update()
```

**消息协议不变**是这套设计的关键：`Majiang.Player` 的 `action(msg, callback)` 已经是
一个干净的「引擎 → 玩家」协议，温岭引擎只要发同样的消息，人类玩家控制器
（`majiang-ui/lib/player.js`）就能复用大部分。

### 规则集注册表

```js
Majiang.Rulesets.register('riichi', {
    name: '日本立直麻将',
    engine: majiang-core,
    ui:     majiang-ui,
    rules:  /* 规则表单 schema，供规则页动态渲染 */
});
Majiang.Rulesets.register('wenling', { name: '温岭麻将', engine: wenling, ui: wenlingUI, rules });
```

首页与规则页从注册表渲染下拉框，选择存 `localStorage['Majiang.ruleset']`。

### 视图为什么不共用

日麻视图的信息结构是：宝牌指示牌、立直棒、供托、门风、河、副露。
温岭需要：**财神指示（翻出的那张）、四家花牌区、胡头/台数面板、16/17 张手牌排布、
腊子提示、两两差额结算表**。两者共有部分只有「牌图、手牌渲染、河、副露、控制条、音效」，
可以抽成公共组件复用；盘面布局必须各写一套。

## 温岭规则 → 实现落点

| 规则条目 | 落点 | 难度 |
|:--|:--|:--|
| 144 张（含 8 花） | `Shan` 牌组构造 + 花牌类型 | 低 |
| 庄 17 / 闲 16，翻财神 | `Shan` 配牌 + `Game.qipai` | 低 |
| 补花（牌墙尾） | `Shan` 尾补 + `Game` 补花循环 | 中 |
| 杠头补牌（牌墙头） | `Shan` 头摸 | 低 |
| 财神万能牌 | 和牌判定需通配搜索；向听需重算 | **高** |
| 无财神=硬胡，台数加倍 | `Score` 分支 | 低 |
| 胡头（明刻 2/4、暗刻 4/8、杠 8/16/16/32、花 4、将 2） | `Score.base_hutou()` | 中 |
| 台数（花 1/张、门风刻 1、平胡 1、自摸财神 1、双财神 1、杠开 1、抢杠 1、对对 2、混一色 2、清一色 4、闹闹 1/张） | `Score.tai()` | 中 |
| 分数 = 胡头 × 2^台数 | `Score.total()` | 低 |
| 闲家两两差额结算 | `Score.settle()` | 中 |
| 腊子封顶 | `Score` 特殊分支 | 低 |
| 一炮一响（逆时针优先） | `Game` 和了多重判定 | 中 |
| 剩 8 墩流局 | `Game` 流局条件 | 低 |
| 吃牌限制（不可吃回原牌） | `Game.get_chi_mianzi` 等价逻辑 | 低 |
| 闹闹模式 | `Game` 开局判定 + `Score.tai()` | 低 |
| AI | 牌效 + 财神权重；16 张向听 | 中 |

## 分阶段（可玩闭环优先）

| 阶段 | 内容 | 预估 |
|:--|:--|:--|
| P0 | 规则集注册表 + 首页选择 + 路由到不同对局页 | 0.5 天 |
| P1 | 温岭引擎：牌组、牌山、配牌、补花、杠、出牌合法性 | 3 天 |
| P2 | 和牌判定（16 张 + 七对 + 财神通配） | 4 天 |
| P3 | 胡头 / 台数 / 腊子 / 结算（含两两差额） | 3 天 |
| P4 | 局进行：庄闲轮转、连庄、流局、一炮一响 | 2 天 |
| P5 | 温岭视图：花牌区、财神指示、胡头台数面板、17 张手牌 | 4 天 |
| P6 | AI 第一版（牌效 + 财神权重） | 3 天 |

P0-P4 是「能自己和自己打完一局」的闭环，约 2 周；P5 之后才能在浏览器里正常玩，全量约 3 周。

**更省事的替代方案**：温岭单独做一个 `wenling.html` 页面，不和日麻共用盘面组件。
这能把 P5 压到 2 天，代价是两套页面各自维护。

## 待确认（阻塞项）

1. **胡牌张数**：规则写「每人 16 张、庄 17 张」，但胡牌型写「4 组面子 + 1 对将」= 14 张。
   这两条不能同时成立。是 16 张制（5 面子 + 1 将 = 17 张成牌、七对 = 8 对），
   还是「16 张」里含 2 张花牌、实际手牌 14 张？
2. **财神是牌种还是单张**：翻出 5 万，是 4 张 5 万都成财神，还是只有翻开的这一张？
   （「双财神」「三得腊子」暗示是牌种。）
3. **硬胡**：「台数翻倍」与「无财神 +1 台」两处重复表述，是 +1 台、×2，还是两者都算？
4. **腊子封顶分**：具体多少分？（规则只写「按约定封顶分」）
5. **闹闹模式**：财神翻到花牌时，中发白三种刻子是否都各 +1 台？
6. **七对胡头**：七对型的每一对按不按「将牌对子」计胡头？
